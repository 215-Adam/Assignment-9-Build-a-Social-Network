Design Memo: Social Network Graph

A graph is the natural structure for a social network because the data is really about relationships, not just about people. Each person is a node and each friendship is an edge. Friendships are mutual, so the edges are undirected, which I modeled by adding each person to the other's friends list. A graph places no limit on how many connections a person can have or how those connections overlap, and that matches real friend groups, with clusters, shared friends, and loops such as Morgan, Casey, and Riley all knowing each other.

A plain list would only store the people. To find someone's friends, I would need a separate list of pairs and would have to scan all of it every time. A tree doesn't fit either, because it assumes a hierarchy where every node has exactly one parent and there are no cycles. Alex can be friends with both Jordan and Taylor while Jordan and Taylor are also friends, which forms a cycle a tree can't represent.

I used an adjacency list: a dictionary that maps names to Person objects, where each Person holds a list of friends. Looking up a person by name is O(1) on average, and memory grows with the number of friendships, which suits sparse networks. The trade-off is that checking whether two people are already friends means scanning a friends list, which is O(k) for k friends. I needed that check to prevent duplicates. An adjacency matrix would answer it in O(1), but it costs n-squared memory and has to be resized whenever someone joins. Printing visits every person and every edge, so it runs in O(V + E). Each friendship is stored twice, which is the price of mutual relationships.
